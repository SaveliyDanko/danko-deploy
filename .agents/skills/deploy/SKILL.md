# deploy — раскатка панели на прод-VPS (Ansible)

Цель: обновить саму панель с управляющей машины, не полагаясь на её веб-терминал. Перед изменением
Ansible сохраняет named volumes и секреты, возвращает старый backend после снимка, затем обновляет
код и проверяет `/api/health`. Под капотом — `deploy/ansible/site.yml`. Полный контекст —
[docs/DEPLOY.md](../../../docs/DEPLOY.md) и [deploy/ansible/README.md](../../../deploy/ansible/README.md).

> **Это деплой наружу — необратимое, видимое наружу действие.** Сначала покажи план (что и куда
> катишь), затем выполняй. На полный деплой/выкатку кода — спрашивай подтверждение, если пользователь
> уже явно не сказал «деплой/выкатывай». `check` (dry-run) можно гонять без подтверждения.

## Аргументы (`$deploy <режим>`)

| Аргумент | Команда ansible               | Что делает                                                         |
| -------- | ----------------------------- | ------------------------------------------------------------------ |
| (пусто)  | `ansible-playbook site.yml`   | **Полный деплой**: Docker, Traefik, секреты, код, сборка, запуск   |
| `code`   | `… --tags backup,code,deploy` | Pre-deploy backup, обновление кода и пересборка без Docker/Traefik |
| `backup` | `… --tags backup`             | Только согласованный снимок данных, без обновления                 |
| `check`  | `… --check`                   | Dry-run: показать, что изменится, ничего не меняя                  |

## Где взять пароль ansible-vault (неинтерактивно)

`vault.yml` зашифрован, поэтому ansible нужен пароль. Запрашивать его интерактивно
(`--ask-vault-pass`) в этом окружении **нельзя** — бери из файла и передавай `--vault-password-file`.

Ищи файл пароля **в этом порядке** (первый существующий — побеждает):

1. `deploy/ansible/.vault-pass` (в `.gitignore`, не коммитится)
2. `~/.dankodeploy-vault-pass`

Файл — одна строка: сам пароль vault. Если **ни одного нет** — НЕ запускай playbook.
Сообщи пользователю и предложи создать его, например:

```bash
printf '%s' 'ПАРОЛЬ_VAULT' > deploy/ansible/.vault-pass && chmod 600 deploy/ansible/.vault-pass
```

(Можно также проверить env `DANKODEPLOY_VAULT_PASS` — если задана, записать её во временный
0600-файл и передать его как `--vault-password-file`, потом удалить. Но дефолт — файл выше.)

## Что делать

### 1. Preflight (быстрые read-only проверки — не запускай деплой, если что-то не так)

Выполни и проверь:

- `command -v ansible-playbook` — ansible установлен? Если нет — стоп, скажи `pip install ansible`.
- Конфиги на месте: `deploy/ansible/inventory.ini`, `deploy/ansible/group_vars/dankodeploy.yml`,
  `deploy/ansible/group_vars/vault.yml`. Если `inventory.ini`/`vault.yml` нет — пользователь не
  настроил стенд (см. `*.example` рядом), стоп с понятным сообщением.
- `vault.yml` действительно зашифрован: первая строка должна быть `$ANSIBLE_VAULT;1.1;AES256`.
  Если файл в открытом виде — предупреди (это утечка секрета), но это его выбор.
- Файл пароля vault найден (см. раздел выше). Нет — стоп с инструкцией создать.
- Host из `inventory.ini` уже есть в `~/.ssh/known_hosts`. Если ключ неизвестен или изменился —
  **стоп**. Не запускай `ssh-keyscan` с автоматическим доверием: попроси пользователя сверить
  fingerprint через консоль VPS-провайдера и один раз подключиться обычным `ssh`.
- Для `code` проверь `git status --short`, текущую ветку и наличие нужного commit в удалённой
  `dankodeploy_branch`: Ansible выкатывает remote-ветку, а не незакоммиченные локальные файлы.

Подтяни домен/repo/ветку из `group_vars/dankodeploy.yml` (`dankodeploy_domain`,
`dankodeploy_repo`, `dankodeploy_branch`) и адрес VPS из `inventory.ini` — чтобы показать в плане.

### 2. Показать план и (для деплоя) спросить подтверждение

Кратко: «Деплой на `<домен>` (VPS `<host>`), ветка `<branch>`, режим
`<полный|code|backup|check>`; backup: `<путь>`, хранение: `<дни>`». Для полного деплоя и `code`
дождись «да», если пользователь не дал явного разрешения. `backup` и `check` можно запускать сразу,
когда пользователь явно вызвал соответствующий режим.

### 3. Запуск

Из каталога `deploy/ansible` (НЕ делай `cd` отдельной командой — задай рабочий каталог одной
строкой через `bash -c 'cd … && …'` либо запускай с абсолютными путями, чтобы не ловить
permission-промпт на `cd`). Базовая команда:

```bash
ansible-playbook site.yml --vault-password-file <файл-пароля> [<доп-флаги-режима>]
```

- полный: без доп-флагов
- `code`: `--tags backup,code,deploy`
- `backup`: `--tags backup`
- `check`: `--check`

Деплой долгий (сборка образов на сервере) — запускай с увеличенным таймаутом
(`timeout: 600000`) и не дёргай повторно, пока идёт. Лог ansible (`stdout_callback: yaml`)
стримь пользователю; на падении покажи упавшую task и причину.

### 4. Итог

- При успехе: укажи URL панели, путь созданного snapshot из Ansible-лога и результат health-check.
- При ошибке: какая task упала, вероятная причина (DNS/A-запись для LE, доступ по SSH,
  host-key mismatch, свободное место, занятые 80/443, неверный vault-пароль →
  `Decryption failed`) и что проверить. Не запускай деплой повторно вслепую.
- Восстановление backup перезаписывает данные. Никогда не выполняй его без отдельной явной просьбы,
  выбранного snapshot и подтверждения пользователя.

## Чего НЕ делать

- Не печатать и не логировать содержимое файла пароля vault, `vault.yml`, `secrets/`.
- Не коммитить `.vault-pass`, `inventory.ini`, `vault.yml` (всё в `.gitignore`).
- Не ослаблять шифрование vault и не переходить на открытый пароль ради автоматизации.
- Не передавать пароль через `--extra-vars` или в командной строке (виден в `ps`/истории) —
  только `--vault-password-file`.
- Не запускать `db:generate`/`db:migrate` и не трогать прод-данные вручную — схему катит entrypoint.
- Не запускать `docker compose down -v`: флаг `-v` удаляет persistent volumes.
- Не выполнять self-deploy из веб-терминала DankoDeploy — Ansible запускается снаружи.
