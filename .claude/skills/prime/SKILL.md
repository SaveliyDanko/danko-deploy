# Prime

## Goal

Построить в свежей сессии минимальную карту «где что лежит», читая только индексы и точки
входа проекта. Не сканировать и не анализировать исходный код. Остановиться, как только контекста
достаточно, чтобы выбрать основной файл и одну релевантную доку для следующей задачи.

## Rules

- Во время prime-прохода открывать только:
  - `AGENTS.md`;
  - `CLAUDE.md` — только как дополнительный указатель, если файл существует;
  - `README.md`;
  - `docs/CODEMAP.md`;
  - `deploy/README.md` — только если уже названная задача касается раскатки самой панели;
  - `deploy/ansible/README.md` — только если задача явно касается Ansible-раскатки.
- Не открывать исходники в `apps/server/src/`, `apps/web/src/`, `packages/core/src/`,
  `packages/db/src/`, `packages/shared/src/` и не просматривать содержимое остальных файлов
  в `apps/` или `packages/`.
- Не запускать `grep`, `rg`, `find`, `git grep`, `tree` или аналогичный поиск/сканирование по
  кодовой базе. Не сверять документацию с исходниками и не читать `git log`/`git diff`.
- Считать документацию иерархичной: сначала корневые точки входа и индекс; листовые документы
  только назвать как следующий шаг, но не открывать в этом проходе.
- Не вносить никаких правок, не устанавливать зависимости и не запускать сборку или тесты.
- Держать проход коротким: несколько точечных чтений, не аудит репозитория.
- Остановиться сразу после подготовки требуемого формата вывода.

## Steps

### 1. Точки входа

Прочитать по порядку:

1. `AGENTS.md` — обязательные инструкции Codex, обзор монорепо, команды проверок и
   верхнеуровневая карта.
2. `CLAUDE.md` — необязательный дополнительный указатель на документацию; не считать его
   инструкциями Codex и не читать, если файла нет.
3. `README.md` — назначение продукта, возможности, стек, структура и раздел
   «Дальнейшее развитие».

Особенно зафиксировать из `AGENTS.md` реальные части монорепо и точки входа:
`apps/server`, `apps/web`, `packages/shared`, `packages/db`, `packages/core`. Не переходить по
ссылкам на их исходники.

### 2. Карта документации и файлов

Прочитать `docs/CODEMAP.md`. Это заменяет отсутствующий `docs/README.md`: файл является плоским
индексом `путь → назначение` и содержит готовую таблицу «задача → файл».

Использовать карту для выбора вероятных файлов, но не открывать ни один указанный исходник и не
переходить по ссылкам в листовые документы.

### 3. Текущее состояние и следующая задача

Отдельного status/progress/roadmap/changelog-файла в репозитории нет. Поэтому:

- считать раздел «Возможности» в уже прочитанном `README.md` только грубым описанием реализованного;
- считать раздел «Дальнейшее развитие» списком направлений, а не упорядоченным бэклогом;
- явно сообщить, что авторитетная текущая задача в репозитории не зафиксирована;
- не придумывать статус и не выводить его из истории git или исходного кода.

Если пользователь уже назвал задачу, сопоставить её с `docs/CODEMAP.md` и указать вероятный
основной файл и одну следующую доку, всё ещё не читая их.

### 4. Спуск только по индексам

Внутри `docs/` нет вложенных `README.md`-индексов, поэтому дальше по этой ветке не спускаться.

Только для уже названной задачи по раскатке панели прочитать `deploy/README.md`; если задача
именно про Ansible, после него прочитать `deploy/ansible/README.md`. Это локальные точки входа
ветки деплоя. Остальное оставить до начала конкретной работы.

На prime-проходе явно не читать:

- `docs/ARCHITECTURE.md` — тяжёлый лист с полной архитектурой;
- `docs/SERVICE-SPEC.md` — лист по подготовке сервисов и конфигурации проектов;
- `docs/DEPLOY.md` — лист по production-раскатке панели;
- любые исходники, тесты, конфиги и схемы внутри `apps/` и `packages/`;
- содержимое `deploy/`, кроме двух условно разрешённых `README.md` выше.

## Output

Выдать компактное резюме без преамбулы:

1. **Что за проект** — 1–2 предложения.
2. **Архитектура** — по одной строке на backend, frontend, shared-схемы, БД и core.
3. **Где что лежит** — сжатая карта «задача → основной файл + релевантная дока», опирающаяся
   на готовую навигационную таблицу из `docs/CODEMAP.md`.
4. **Текущее состояние и следующая задача** — реализованные возможности и направления из
   `README.md`, с явной оговоркой, что отдельного статус-файла и авторитетной следующей задачи нет.
5. **Как проверять** — команды гейта из `AGENTS.md`: `pnpm typecheck`, `pnpm lint`, `pnpm test`,
   `pnpm build`; упомянуть дополнительные проверки только если они прямо относятся к названной
   задаче.
6. **Куда дальше** — назвать ровно одну доку для следующей задачи, не читая её:
   `docs/ARCHITECTURE.md` для устройства приложения, `docs/SERVICE-SPEC.md` для формата сервиса
   или `docs/DEPLOY.md` для раскатки панели. Остальные документы загружать по требованию.

В конце спросить, над чем работать. Если задача уже названа, вместо вопроса указать конкретный
основной файл из `docs/CODEMAP.md` и выбранную следующую доку, всё ещё без их чтения.
