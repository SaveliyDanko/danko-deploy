# DankoDeploy CLI

`@dankodeploy/cli` — JSON-first интерфейс между LLM-агентом и HTTP API DankoDeploy. CLI
запускается из каталога управляемого проекта, находит привязку к конкретному деплою, выполняет
разрешённую операцию через панель и возвращает результат в машиночитаемом виде.

## Как это устроено

```text
LLM-агент
  └─ dankodeploy <command>
       ├─ ищет вверх по каталогам .dankodeploy.json
       ├─ берёт сырой токен из DANKODEPLOY_TOKEN
       ├─ вызывает REST API панели с Authorization: Bearer ...
       └─ печатает JSON в stdout или ошибку в JSON в stderr
```

Файл `.dankodeploy.json` связывает репозиторий с одной сущностью «деплой» — парой
`проект × сервер`. Поэтому одна и та же команда `dankodeploy deploy` из разных репозиториев
обращается к нужному проекту и серверу без передачи ID при каждом запуске.

Долгие операции панель запускает в фоне и сразу возвращает `runId`. По умолчанию CLI раз в секунду
читает историю запусков, ждёт конечного статуса и только после этого возвращает полный `DeployRun`
с логом. Таймаут ожидания — 900 секунд; HTTP-запроса — 30 секунд.

## Установка из репозитория

Нужен Node.js 20 или новее. Пока пакет не опубликован в npm, CLI собирается и устанавливается из
локального клона DankoDeploy:

```bash
pnpm --filter @dankodeploy/cli build
npm install -g ./apps/cli
dankodeploy help
```

Собранный пакет не имеет runtime-зависимостей от монорепозитория.

## Токен автоматизации

Сгенерируйте пару «сырой токен + SHA-256»:

```bash
pnpm gen-token
```

Команда показывает два значения:

- `DANKODEPLOY_TOKEN=ddp_...` — сырой токен для окружения CLI;
- `DANKODEPLOY_AUTOMATION_TOKEN_HASH=...` — SHA-256 для backend панели.

На машине панели добавьте хэш в `.env` и перезапустите backend:

```env
DANKODEPLOY_AUTOMATION_TOKEN_HASH=<sha256-из-pnpm-gen-token>
```

Для production Ansible то же значение задаётся как `dankodeploy_automation_token_hash` в
`deploy/ansible/group_vars/dankodeploy.yml`. Сырой токен туда не записывается.

На машине или сервере LLM-агента задайте:

```bash
export DANKODEPLOY_TOKEN=ddp_...
```

Сырой токен нельзя класть в `.dankodeploy.json`, репозиторий, логи или prompt. Для ротации
сгенерируйте новую пару, замените хэш на панели и перезапустите backend — старый токен сразу
перестанет проходить проверку.

### Ограничения токена

Bearer-токен имеет узкий allowlist:

- чтение карточки конкретного проекта, конкретного деплоя, его запусков и бэкапов;
- `deploy`, `provision`, `undeploy`, `backup`, `restore` и запись уже сохранённого `.env` на сервер.

Токен не может получить список всех проектов/деплоев, читать содержимое `.env`, управлять
серверами или SSH-ключами, вызывать административные эндпоинты и подключаться к `/ws` или
веб-терминалу. Сейчас на панели настраивается один ротируемый токен автоматизации.

## Подключение проекта

Deployment ID можно взять из панели. В корне управляемого репозитория выполните:

```bash
dankodeploy init \
  --url https://deploy.example.com \
  --deployment <deployment-id>
```

Перед записью конфигурации CLI запрашивает деплой у панели и проверяет токен, URL и ID. Результат:

```json
{
  "version": 1,
  "panelUrl": "https://deploy.example.com",
  "deploymentId": "V1StGXR8_Z5jdHi6B-myT"
}
```

Файл `.dankodeploy.json` не содержит секретов, поэтому его можно коммитить. CLI ищет файл от
текущего каталога вверх до корня файловой системы: команды работают и из вложенных директорий.
Для осознанной перезаписи существующей привязки используется `init --force`.

## Команды

| Команда               | Что возвращает или делает                                                                      |
| --------------------- | ---------------------------------------------------------------------------------------------- |
| `config`              | Найденный путь и конфигурацию; `tokenConfigured` сообщает только факт наличия env-токена       |
| `status`              | Детали деплоя и текущий runtime-статус, git-ревизию и версию; backend опрашивает сервер по SSH |
| `context`             | Детали деплоя, 5 последних запусков и 5 последних бэкапов                                      |
| `runs`                | Последние 20 операций деплоя; лимит меняется через `--limit N`                                 |
| `backups`             | Последние 20 бэкапов проекта; лимит меняется через `--limit N`                                 |
| `deploy`              | Обновить код и перезапустить сервис согласно конфигурации проекта                              |
| `provision`           | Выполнить первичную раскатку (`git clone`)                                                     |
| `undeploy`            | Остановить или снять сервис согласно его типу                                                  |
| `backup`              | Запустить настроенный бэкап артефактов                                                         |
| `restore --backup ID` | Восстановить бэкап; `--artifact name` можно повторять для выбора артефактов                    |
| `env-deploy`          | Записать уже сохранённый в панели `.env` в `<workdir>/.env`; содержимое CLI не получает        |

Для `context` доступны `--runs N` и `--backups N`. Фоновые операции поддерживают:

```bash
dankodeploy deploy --timeout 1200
dankodeploy backup --no-wait
dankodeploy restore --backup <id> --artifact db --artifact media
```

`--no-wait` возвращает `{ runId, status: "running" }` сразу. После него агент должен проверять
завершение через `dankodeploy runs`; считать сам факт получения `runId` успешным деплоем нельзя.

## JSON и коды завершения

Обычный результат печатается в `stdout`. Ошибка CLI или HTTP API печатается в `stderr` в формате:

```json
{
  "ok": false,
  "error": "Требуется аутентификация",
  "status": 401,
  "details": { "error": "Требуется аутентификация" }
}
```

Коды процесса:

- `0` — команда выполнена или фоновая операция завершилась успешно;
- `1` — неверные аргументы, конфигурация, сеть, авторизация или ошибка HTTP API;
- `2` — операция была запущена, но завершилась со статусом `failed`.

LLM-агент должен проверять и exit code, и поле `ok`, а при неуспешном запуске анализировать
`run.log`. Перед изменяющей состояние командой полезно сначала вызвать `dankodeploy context`.

## Рекомендуемый фрагмент для `AGENTS.md` проекта

```md
## DankoDeploy

- Перед операциями вызови `dankodeploy context`.
- Для раскатки используй `dankodeploy deploy` и проверь exit code и `run.status`.
- Не печатай и не записывай `DANKODEPLOY_TOKEN`.
- `undeploy`, `restore` и `env-deploy` выполняй только по явной задаче пользователя.
- Не считай ответ `--no-wait` завершением операции; проверь её через `dankodeploy runs`.
```

## Частые ошибки

- `401 Требуется аутентификация` — токен не задан, не совпадает с хэшем панели или backend не
  перезапущен после изменения env.
- `403 Токен автоматизации не имеет доступа` — команда обращается к API вне CLI-allowlist.
- `.dankodeploy.json не найден` — выполните `init` в репозитории или его родительском каталоге.
- Таймаут операции — сам backend-run может продолжаться; проверьте `dankodeploy runs` перед
  повторным запуском, чтобы не создать дублирующее действие.
