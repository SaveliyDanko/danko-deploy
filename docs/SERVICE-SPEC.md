# Спецификация деплоя сервисов в DankoDeploy

> Этот документ — **контракт между вашим репозиторием и панелью**. Если привести проект к
> описанной здесь форме, панель сможет деплоить, мониторить и бэкапить его без сюрпризов.
>
> Как работает панель в двух словах: она подключается к серверу **по SSH**, делает `git pull`
> в рабочей директории проекта и выполняет shell-команды (шаги деплоя, бэкапа). **Никаких
> агентов на сервере нет.**
>
> Основной (рекомендуемый) путь — **Docker Compose**. Доставка кода — **git pull на сервере**.
> Раскладка — **`/srv/<проект>`**.

---

## 1. TL;DR — минимум для запуска

Чтобы docker-compose проект заработал с панелью, достаточно:

- [ ] Код в **git-репозитории**, склонированном на сервер в **`/srv/<имя-проекта>`**.
- [ ] В корне репозитория — **`docker-compose.yml`**.
- [ ] **`.env`** лежит на сервере (создан вручную), **в git его нет** (только `.env.example`).
- [ ] На сервере установлены **Docker Engine** и **Docker Compose plugin**, а SSH-пользователь
      может выполнять `docker info` без `sudo`.
- [ ] У сервисов в compose — **`restart: unless-stopped`**.
- [ ] В панели заведён проект: **kind = `docker-compose`**, **workdir = `/srv/<имя-проекта>`**.

Дальше жмёте **Deploy** — панель сама сделает `git pull` + `docker compose up`. Полный список
проверок — в разделе [9. Чек-лист готовности](#9-чек-лист-готовности-проекта).

## 2. Как панель работает с вашим проектом

Понимание механики объясняет все требования ниже («почему именно так»).

- **Всё выполняется по SSH в `workdir`.** Каждый шаг деплоя/бэкапа — обычная shell-команда,
  запущенная из рабочей директории проекта на сервере.
- **Ненулевой код выхода любого шага → деплой `failed`** и прерывается. Поэтому команды должны
  честно возвращать код выхода и по возможности быть идемпотентными. Лог стримится в браузер построчно.
- Панель оперирует тремя сущностями:
  - **Деплой** — обновить код и перезапустить сервис.
  - **Статус/сводка** — опрашивается по запросу (не постоянный мониторинг сервиса).
  - **Бэкап** — вручную и по cron-расписанию.
- **Источник конфигурации сейчас — UI** (поле `config` хранится в БД как JSON). Файла-манифеста
  в репозитории панель пока не читает (см. [раздел 7](#7-манифест-dankodeployyml-рекомендуемый-будущий-контракт)).

Поле `config` ↔ что делает:

| Поле | Назначение |
|------|-----------|
| `workdir` | Рабочая директория на сервере (где `git pull` и все команды). **Обязательно.** |
| `composeFile` | Имя compose-файла, если не `docker-compose.yml` (добавляет `-f <file>`). |
| `systemdUnit` | Имя systemd-юнита (для kind=systemd). |
| `deploySteps` | Кастомные шаги деплоя — **полностью заменяют** дефолтные для kind. |
| `undeploySteps` | Кастомные шаги undeploy — **полностью заменяют** дефолтные для kind. |
| `backupArtifacts` | Список именованных артефактов: `[{name, backupCommand ({{OUT}}), restoreCommand? ({{IN}})}]`. |
| `backupCommand`/`restoreCommand` | LEGACY: одиночная пара команд (оборачивается в артефакт `default`). |
| `backupCron` | Cron-выражение для авто-бэкапов. |
| `meta` | Справочная метаинформация: порты, контейнеры, env-переменные (чек-лист), чек-лист перед раскаткой, ссылки, заметки. На деплой не влияет. |

**Проект (карточка) vs. деплой.** Проект в панели — это **карточка без сервера**: метаинформация,
git-репозиторий, описание и конфиг раскатки (поля из таблицы выше) + общий шаблон `.env`. Чтобы
раскатать проект на сервер, во вкладке **«Деплои»** создаётся **деплой** = пара `проект × сервер`.
Раскатка (Deploy / «Раскатить» / Undeploy), бэкап и восстановление, запись `.env` на сервер — всё
выполняется **со страницы деплоя**, а статус и история раскаток ведутся по каждому деплою отдельно.

**Метаинформация и раскатка на несколько серверов.** В форме проекта (блок «Метаинформация») можно
вести порты, контейнеры, список env-переменных, чек-лист перед раскаткой и ссылки (домен/дашборды) —
чтобы быстро сориентироваться. Чтобы раскатать один проект на несколько VPS, создайте **несколько
деплоев** этого проекта (по одному на сервер) — у каждого своя история раскаток, общий шаблон `.env`
проекта пишется на сервер выбранного деплоя. История бэкапов общая на проекте, но каждая запись
помнит, с какого деплоя (сервера) снята.

## 3. Раскладка на сервере и доставка кода

**Соглашение: `workdir = /srv/<имя-проекта>`.** Можно использовать другой путь, но единообразие
сильно упрощает поддержку и автоматизацию.

- **`workdir` обязан быть git-репозиторием.** Панель определяет версию проекта через
  `git rev-parse --short HEAD` в `workdir`. Если это не git-репо — ревизия в сводке будет пустой,
  а дефолтный `git pull` упадёт. Первичную настройку (`git clone`) панель может сделать **сама** —
  см. §3.1 «Первичная раскатка из Git».
- **Доставка кода — `git pull --ff-only`.** Панель **не загружает файлы** на сервер — она тянет уже
  **запушенный в remote** код. Следствия:
  - Коммитьте и пушьте изменения **до** нажатия Deploy.
  - `--ff-only` намеренно падает, если в `workdir` есть локальные правки или история разошлась —
    **не редактируйте файлы прямо на сервере** (см. антипаттерны).
- **Права.** SSH-пользователь панели должен **владеть** `workdir` и иметь доступ к git remote
  (для приватного репо — см. §3.1; для обновлений `git pull` доступ к remote должен оставаться).

### 3.1 Первичная раскатка из Git (`git clone` по кнопке)

Чтобы не клонировать репозиторий на сервер вручную, при создании проекта можно указать **источник
кода**. Тогда на странице проекта появляется кнопка **«Раскатить»** — панель сама выполнит
`git clone` в `workdir`. Дальше проект обслуживается обычным **Deploy** (`git pull`).

Два источника:

- **Public git** — публичный репозиторий по https-URL (`https://github.com/me/app.git`).
  Авторизация не нужна, ключи не требуются.
- **Private git** — приватный репозиторий по ssh-URL (`git@github.com:me/app.git`) с **Git deploy-ключом**:
  1. Вкладка **«Git-ключи»** → «Сгенерировать» (рекомендуется ed25519). Приватная часть шифруется
     в БД панели (AES-256-GCM) и наружу не отдаётся.
  2. Скопируй публичную часть и добавь её в репозитории как **Deploy key**
     (GitHub: *Settings → Deploy keys*; GitLab: *Settings → Repository → Deploy keys*). Read-only достаточно.
  3. Создай проект с источником **Private git**, укажи ssh-URL и выбери этот ключ.

Как это работает под капотом (private): панель кладёт приватный ключ во **временный файл** на сервере
(`chmod 600`) и клонирует с `GIT_SSH_COMMAND='ssh -i <файл> -o IdentitiesOnly=yes -o
StrictHostKeyChecking=accept-new'`; файл **удаляется сразу после** clone (даже при ошибке). Содержимое
ключа в логи не пишется. `~/.ssh/config` на сервере не трогается.
При последующих деплоях панель так же временно подставляет этот ключ для `git pull`, поэтому
разворачивать приватный deploy-ключ в `~/.ssh` на сервере не нужно.

Ограничения:
- Раскатка работает только если **`workdir` пуст или не существует**. Если там уже что-то есть
  (в т.ч. готовый git-репо) — раскатка падает с понятной ошибкой; используй обычный **Deploy**.
- Источник опционален. Если код уже лежит на сервере — выбери «Уже на сервере (не клонировать)».
- Ветку можно указать (`--branch`); пусто — ветка по умолчанию репозитория.

## 4. Docker Compose — основной путь

Рекомендуемый способ: единообразно, статус/логи/бэкапы работают лучше всего.

На сервере заранее должны быть доступны:

```bash
docker --version
docker compose version
docker info
```

Команды должны работать именно под тем SSH-пользователем, которого вы указали в панели.

### 4.1 Требования к репозиторию

- В **корне репозитория** — `docker-compose.yml`. Если файл называется иначе (например
  `docker-compose.prod.yml`) — укажите его в `config.composeFile`, и панель добавит `-f <file>`
  во все compose-команды.
- **`.env` — вне git.** В репозитории держите `.env.example` (шаблон без секретов); реальный
  `.env` живёт на сервере рядом с compose-файлом. Чтобы compose проброс переменных в контейнер
  работал — добавьте `env_file: [.env]` в сервис (см. [раздел 4.6](#46-как-задать-env)).
- **Почему это безопасно:** `git pull` обновляет код, но **не трогает** `.env` (он в `.gitignore` и
  не отслеживается). Так секреты и окружение переживают деплои.
- **Сборка образов.** Дефолтный деплой делает `pull --ignore-buildable` и затем `up -d --build`:
  registry-образы подтягиваются, а сервисы с `build:` собираются **на сервере**. На слабом VPS это
  может упереться в RAM/CPU (см. антипаттерны) — тогда собирайте образы в CI и тяните готовые из
  registry через кастомные `deploySteps`.

### 4.2 Что именно выполняет панель (дефолтный цикл)

Для kind=`docker-compose` без `deploySteps` панель выполняет **ровно эти 4 шага** (в `workdir`):

```
1. git pull --ff-only
2. docker compose [-f <composeFile>] pull --ignore-buildable
3. docker compose [-f <composeFile>] up -d --build
4. docker image prune -f
```

Undeploy для kind=`docker-compose` выполняет:

```
docker compose [-f <composeFile>] down --remove-orphans
```

Volumes не удаляются. Если нужно удалять дополнительные ресурсы, задайте `config.undeploySteps`.

Если нужны дополнительные действия (например, **миграции БД**), задайте `config.deploySteps`.
⚠️ **Кастомные `deploySteps` полностью заменяют дефолт** — `git pull` и `compose up` нужно
прописать в них самостоятельно. Пример с миграцией:

```yaml
deploySteps:
  - { name: "Pull",     run: "git pull --ff-only" }
  - { name: "Build",    run: "docker compose up -d --build" }
  - { name: "Migrate",  run: "docker compose exec -T app npm run migrate" }
```

### 4.3 Чтобы статус показывался `running`

Панель определяет статус командой `docker compose [-f file] ps --format "{{.Name}} {{.State}}"`:
**running**, если хотя бы один контейнер в состоянии running/up; пустой вывод → **stopped**.

Следствия:
- Сервисы должны **оставаться поднятыми** → ставьте **`restart: unless-stopped`** (или `always`).
- Короткоживущие one-shot контейнеры (выполнили задачу и вышли) дадут статус `stopped`, даже если
  «всё ок» — они не должны быть основным сервисом.

### 4.4 Healthcheck и рестарт-полиси

```yaml
services:
  app:
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
      interval: 30s
      timeout: 5s
      retries: 3
    depends_on:
      db:
        condition: service_healthy
  db:
    restart: unless-stopped
```

- `restart: unless-stopped` — обязательно для всех долгоживущих сервисов.
- `healthcheck` — полезен для устойчивости и порядка старта (`depends_on: condition: service_healthy`).
- ⚠️ **Оговорка:** панель **не читает** healthcheck — она смотрит только поле `State` из `compose ps`.
  Контейнер в статусе `running (unhealthy)` панель всё равно покажет как running.

### 4.5 Бэкап и восстановление (именованные артефакты)

Бэкап настраивается **списком именованных артефактов** (`config.backupArtifacts`) — например `db` и
`media`. У каждого артефакта своя пара команд: **backup** (`{{OUT}}` = путь к файлу) и опционально
**restore** (`{{IN}}` = путь к файлу). Это нужно приложениям, где БД и медиа — независимые
артефакты, которые бэкапятся/восстанавливаются по отдельности.

**Как работает бэкап.** Один прогон («Сделать бэкап») выполняет команду каждого артефакта по SSH в
`workdir`, скачивает результат в `BACKUP_DIR` панели и удаляет временный файл с сервера. В истории —
**одна запись на прогон** со списком артефактов (`db`, `media`, …) и их размерами.

Пример (артефакты `db` + `media`):

```
# артефакт db
docker compose exec -T db pg_dump -U postgres mydb | gzip > {{OUT}}
# артефакт media
tar czf {{OUT}} -C /srv/myapp media
```

- ⚠️ **`-T` обязателен** в `docker compose exec` — у SSH-сессии нет TTY.
- Если `{{OUT}}` в команде нет — панель сама добавит `> <путь>` в конец.
- `config.backupCron` (например `0 3 * * *`) — авто-бэкап всех артефактов каждый день в 03:00.

**Восстановление.** Кнопка **«Восстановить»** на бэкапе → модалка с выбором артефактов (чекбоксы +
«Все»). По каждому выбранному панель заливает его файл на сервер и выполняет `restoreCommand`
(`{{IN}}` = путь). Можно восстановить **только `db`** без `media`. Действие **перезаписывает данные**,
поэтому с подтверждением.

Пример restore-команд:

```
# db
gunzip -c {{IN}} | docker compose exec -T db psql -U postgres mydb
# media
tar xzf {{IN}} -C /srv/myapp
```

**Совместимость.** Старые проекты с одиночными `backupCommand`/`restoreCommand` работают без правок —
они автоматически считаются артефактом `default`. Старые бэкапы в истории тоже читаются (один
артефакт `default`).

**Загрузка бэкапа файлом.** Помимо снятия с сервера, файл можно **загрузить с ПК** — кнопка
**«Загрузить бэкап»** в разделе «Бэкапы». Файл сохраняется в историю как артефакт `default`
(помечен «загружен»), и из него работает та же кнопка «Восстановить». Удобно для переноса данных
между серверами или восстановления из бэкапа, сделанного вне панели.

### 4.6 Как задать .env

Переменные окружения **не хранятся в git** — их нужно положить на сервер. Есть два пути.

**Через панель (рекомендуется).** На странице проекта — секция **«Переменные окружения (.env)»**:
вводите содержимое `.env`, жмёте **«Сохранить»** (панель шифрует его AES-256-GCM и хранит у себя),
затем **«Записать на сервер»** — файл кладётся в `<workdir>/.env` с правами `600`. Не нужно
заходить по SSH и вводить значения заново при каждом сервере. Контент шифруется тем же
мастер-ключом, что и SSH-секреты.

**Вручную.** Зайти по SSH в `workdir` и создать `.env` (`nano .env` / `scp`).

Чтобы переменные попали **внутрь контейнера**, подключите файл в compose:

```yaml
services:
  app:
    env_file:
      - .env              # весь .env → окружение контейнера
    # либо точечно:
    # environment:
    #   - DATABASE_URL=${DATABASE_URL}   # ${...} берётся из .env рядом с compose
```

> ⚠️ Сам по себе `.env` рядом с `docker-compose.yml` compose использует только для подстановки
> `${VAR}` в сам compose-файл. Чтобы переменные увидело **приложение в контейнере**, нужен
> `env_file` или явный `environment`.

## 5. systemd — альтернатива

Для сервисов, которые запускаются не в контейнерах, а как systemd-юнит.

- **Требования к репо:** код в git-`workdir`; сервис запускается через systemd-юнит; имя юнита —
  в `config.systemdUnit`.
- **Деплой (дефолт):**
  ```
  1. git pull --ff-only
  2. sudo systemctl restart <systemdUnit>
  3. systemctl is-active <systemdUnit>
  ```
  Нужен **passwordless sudo** на `systemctl restart` для SSH-пользователя.
  ⚠️ Если `systemdUnit` не задан — деплой намеренно завершится ошибкой.
- **Статус:** `systemctl is-active <unit>` → running, если `active`; иначе stopped.
- **Пример `backupCommand`:** `pg_dump -U postgres mydb | gzip > {{OUT}}` или
  `tar czf {{OUT}} /var/lib/myapp/data`.

## 6. process — минимальный путь

Запасной вариант для всего, что не ложится на compose/systemd (статические сайты, кастомные скрипты).

- **Требования к репо:** только git-`workdir`. Всю логику задаёте сами через `deploySteps`.
- **Деплой:** по умолчанию — **только `git pull --ff-only`**. Сборку/перезапуск прописываете в
  `deploySteps`:
  ```yaml
  deploySteps:
    - { name: "Pull",  run: "git pull --ff-only" }
    - { name: "Build", run: "npm ci && npm run build" }
    - { name: "Reload", run: "sudo systemctl reload nginx" }
  ```
- **Статус:** всегда **`unknown`** — панель не умеет определять состояние «голого» процесса.
  Если нужен статус — выбирайте docker-compose или systemd.
- **Пример `backupCommand`:** `tar czf {{OUT}} ./data` или `cp ./db.sqlite {{OUT}}`.

## 7. Манифест `dankodeploy.yml` (рекомендуемый будущий контракт)

> ⚠️ **Пока не реализовано:** панель этот файл **не читает**. Сейчас конфигурация задаётся в UI.
> Раздел описывает рекомендуемый формат на будущее, чтобы конфиг жил рядом с кодом и
> версионировался вместе с ним.

Идея — файл `dankodeploy.yml` в корне репозитория с полями **1:1 к текущему `config`**:

```yaml
kind: docker-compose          # docker-compose | systemd | process
workdir: /srv/shop-api
composeFile: docker-compose.prod.yml   # опционально
backupCommand: "docker compose exec -T db pg_dump -U postgres shop | gzip > {{OUT}}"
backupCron: "0 3 * * *"
# deploySteps:                # опционально — заменяет дефолтные шаги
#   - { name: "Pull",  run: "git pull --ff-only" }
#   - { name: "Up",    run: "docker compose up -d --build" }
```

Соответствие «манифест → поле в UI»:

| Поле манифеста | Поле в форме проекта |
|----------------|----------------------|
| `kind` | Тип проекта |
| `workdir` | Рабочая директория |
| `composeFile` | Compose-файл |
| `systemdUnit` | systemd-юнит |
| `deploySteps` | Шаги деплоя |
| `backupCommand` / `backupCron` | Бэкап / расписание |

**Пока заполняйте те же значения в форме UI** — переход на манифест, когда он появится, будет бесшовным.

## 8. Что панель НЕ делает

Чтобы не было ложных ожиданий:

- **Не настраивает инфраструктуру:** firewall, TLS-сертификаты, DNS, reverse-proxy (nginx/Caddy) —
  это на вашей стороне.
- **Управляет `.env` проекта** (секция «Переменные окружения»): хранит зашифрованно, пишет на
  сервер в `<workdir>/.env`. Но **не валидирует** их содержимое и не перезапускает сервис сам —
  после изменения `.env` нужно сделать деплой.
- **Не отслеживает версию.** Поле `version` в сводке **всегда пустое**; отслеживается только
  git-ревизия (`git rev-parse --short HEAD`).
- **Нет полноценного healthcheck-мониторинга.** Статус — это `docker compose ps` (State) /
  `systemctl is-active` / `unknown` для process. Healthcheck из compose не учитывается.
- **Нет авто-отката (rollback).** Откат = переключить git на нужную ревизию (`git revert` / checkout)
  и задеплоить снова.
- **Не делает первичный bootstrap сервера** автоматически — Docker, пользователь, права настраиваются
  один раз вручную (см. [раздел 10](#10-bootstrap-сервера-проекта-кратко)). Но **первичный `git clone`
  репозитория** панель умеет — по кнопке «Раскатать» (см. [§3.1](#31-первичная-раскатка-из-git-git-clone-по-кнопке)).

## 9. Чек-лист готовности проекта

Финальный гейт перед первым деплоем (пример для docker-compose).

**Репозиторий**
- [ ] В корне — `docker-compose.yml` (или имя указано в `composeFile`).
- [ ] `.env` в `.gitignore`, есть `.env.example`.
- [ ] В истории git **нет секретов** (паролей, токенов, ключей).

**Сервер**
- [ ] `workdir = /srv/<name>` существует и **является git-репозиторием**.
- [ ] SSH-пользователь панели **владеет** директорией и имеет доступ к git remote.
- [ ] `.env` создан на сервере рядом с compose-файлом.
- [ ] Установлены Docker и compose-плагин.
- [ ] (для systemd) Настроен passwordless sudo на `systemctl restart <unit>`.

**Сервисы**
- [ ] У долгоживущих сервисов — `restart: unless-stopped`.
- [ ] (опц.) Настроен `healthcheck`.
- [ ] Основной сервис — долгоживущий (виден в `docker compose ps`).

**Панель**
- [ ] Проект заведён: верный `kind`, `workdir`, при нестандартном файле — `composeFile`.
- [ ] Задан `backupCommand` (и `backupCron`, если нужны авто-бэкапы).

**Проверка**
- [ ] Тестовый **Deploy** проходит зелёным.
- [ ] В сводке видна **git-ревизия**.
- [ ] Статус сервиса — **running**.
- [ ] Пробный **бэкап** создаётся и скачивается.

## 10. Bootstrap сервера/проекта (кратко)

Первичная подготовка (делается один раз, вручную; дальше всё делает панель).

**Принципы:**
- Отдельный **непривилегированный пользователь** для деплоя (не root).
- `git clone <repo> /srv/<name>` — код сразу в правильную раскладку.
- **Deploy key** (или HTTPS-токен) на сервере для доступа к приватному repo.
- `.env` создаётся **вручную** из `.env.example`.
- **Docker + compose-плагин** предустановлены.

**Компактный чек-лист bootstrap:**
1. Создать deploy-пользователя, дать ему права на `/srv`.
2. Установить Docker и compose-плагин (или кнопкой **«Установить Docker»** на странице сервера).
3. `git clone` проекта в `/srv/<name>` — или задать **источник кода** и нажать **«Раскатать»** (§3.1).
4. Создать `.env` на сервере (или через панель — секция «Переменные окружения»).
5. (systemd) настроить passwordless sudo на restart юнита.
6. Пройти [чек-лист готовности](#9-чек-лист-готовности-проекта) и сделать первый Deploy.

**Настройка SSH (кнопка «Настроить SSH» на странице сервера).** Применяет рекомендуемые
параметры sshd, чтобы соединение было стабильнее и сервер защищённее:
- поднимает лимиты подключений (`MaxStartups`/`MaxSessions`, `LoginGraceTime`) — всплески и
  брутфорс-атаки не рвут легитимные коннекты (частая причина ошибки «Channel open failure»);
- включает keepalive (`ClientAliveInterval`/`ClientAliveCountMax`) — sshd сам закрывает зависшие сессии;
- ставит **fail2ban** (автобан брутфорс-IP);
- **отключает парольный вход** (`PasswordAuthentication no`) — но ТОЛЬКО если сервер подключён по
  ключу, чтобы не отрезать доступ. На сервере с входом по паролю этот пункт пропускается.

Настройки пишутся в drop-in `sshd_config.d/99-dankodeploy.conf`, конфиг проверяется `sshd -t`,
применяется через `reload` (текущее соединение не рвётся), перед изменением делается бэкап.

## 11. Антипаттерны / частые ошибки

| Проблема | Симптом | Решение |
|----------|---------|---------|
| Сборка на слабом VPS (`up -d --build`) | OOM, деплой висит/падает | Собирать образы в CI, на сервере только `pull` из registry (кастомные `deploySteps`) |
| Секреты в git (`.env` закоммичен) | Утечка ключей | `.env` в `.gitignore`, держать только на сервере; ротировать утёкшие секреты |
| `workdir` — не git-репозиторий | Пустая ревизия в сводке, `git pull` падает | `git clone` в `workdir` |
| `kind = process` | Статус всегда `unknown` | Перейти на docker-compose / systemd, если нужен статус |
| Правки файлов прямо на сервере | `git pull --ff-only` падает | Менять код только через repo (commit → push → deploy) |
| Кастомные `deploySteps` без `git pull`/`up` | Код не обновился или сервис не перезапущен | Включить базовые шаги в `deploySteps` явно |
| `docker compose exec` без `-T` в бэкапе | Ошибка TTY по SSH | Добавить `-T`: `docker compose exec -T db …` |
| One-shot контейнер как основной сервис | Статус `stopped`, хотя «всё ок» | Долгоживущий процесс + `restart: unless-stopped` |

## 12. Приложение: справочник полей `config`

| Поле | Обяз. | Тип | Что делает | Пример |
|------|:----:|-----|-----------|--------|
| `workdir` | да | string | Рабочая директория на сервере (git-репо) | `/srv/shop-api` |
| `composeFile` | нет | string | Нестандартное имя compose-файла (`-f`) | `docker-compose.prod.yml` |
| `systemdUnit` | нет | string | Имя systemd-юнита (kind=systemd) | `telegram-bot.service` |
| `deploySteps` | нет | `{name, run}[]` | Кастомные шаги (заменяют дефолт) | см. §4.2 / §6 |
| `backupCommand` | нет | string | Команда бэкапа (`{{OUT}}` = файл) | `… pg_dump … > {{OUT}}` |
| `backupCron` | нет | string | Cron авто-бэкапов | `0 3 * * *` |

Готовые примеры по каждому типу сервиса — в
[`dankodeploy.config.example.yaml`](../dankodeploy.config.example.yaml).
